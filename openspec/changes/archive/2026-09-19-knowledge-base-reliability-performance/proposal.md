## Why

文档更新中断可能留下新 hash 与不完整内容，后续同步却跳过该文档；索引重建会先发布空索引，工作区关闭还可能影响其他工作区或正在执行的任务。这些问题影响本地知识库的可恢复性和持续可用性，应先于性能调优解决。

## What Changes

- 以文档为单位原子提交 SQLite 业务状态与待投影记录，明确中断恢复与重试边界。
- 重建和更新期间继续提供最近有效的已提交搜索快照，成功后发布新快照。
- 工作区独立管理打开、关闭与在途访问，修正投影落后的状态报告。
- 复用搜索资源、按文档复用元数据、避免未变化文件的全文解码。
- 增加兼容的文档分页与路径搜索，管理页按页加载。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `workspace-service`：补充文档级原子更新、重建发布、生命周期隔离、安全重试和状态一致性要求。
- `document-metadata-search`：补充兼容分页与路径查询、搜索和增量同步优化的行为约束。

## Impact

涉及摄取与同步服务、SQLite 持久层、Lucene 投影、工作区资源管理、文档列表 HTTP 接口及管理页面。保持 Java 17、既有依赖、FIFO 写队列、SQLite 权威数据源、Lucene 可重建投影，以及现有同步 API 的错误与超时语义。

## Problem Statement

用户需要知道失败的导入是否可重试，在重建时继续检索，并在处理一个工作区时正常使用其他工作区。随着文档和分块数量增长，重复数据库查询、重复解码及全量列表加载增加等待时间。

## Solution

让一次文档更新具有明确的完成边界；失败后能够保留或恢复有效内容。搜索在新快照发布前使用上一份有效快照。工作区独立退出并报告真实状态，管理页面通过分页检索定位文档。

## User Stories

1. As a 知识库使用者, I want 失败的文档同步可以再次执行, so that 内容不会因相同 hash 被永久遗漏。
2. As a 知识库使用者, I want 更新期间读取完整的已提交文档状态, so that 不会看到半写入的分块与元数据。
3. As a 知识库使用者, I want 重建索引期间继续搜索, so that 维护操作不会中断查阅。
4. As a 知识库维护者, I want 重建失败后旧索引仍可用, so that 可以安排后续修复。
5. As a 多工作区使用者, I want 一个工作区打开或关闭时其他工作区仍可响应, so that 工作相互隔离。
6. As a 知识库维护者, I want 服务关闭时安全处理在途任务, so that 不会发生任务访问已关闭资源。
7. As a 知识库使用者, I want 永久错误立即返回且重试不重复创建内容, so that 失败行为可预测。
8. As a 知识库维护者, I want 状态页准确反映索引落后及恢复情况, so that 能判断是否需要重试。
9. As a 大型知识库使用者, I want 按页和路径关键字查找文档, so that 不必加载全部文档才能编辑。
10. As a 既有 CLI/API 使用者, I want 老调用方式和元数据优先级继续有效, so that 无需同步修改现有脚本。
11. As a 知识库使用者, I want 未修改文档快速跳过同步, so that 日常维护减少重复处理。

## Testing Decisions

用户已确认以现有 KnowledgeBaseHttpService / HTTP 接口为主要测试边界，仅对故障注入和资源关闭补充底层测试。测试断言完整内容、可恢复性、接口结果及资源生命周期，不绑定私有方法或 SQL 文本。测试执行留待实施阶段明确授权。

引入 Spring Boot、替换存储引擎、升级依赖、跨存储分布式事务、多人协作、新权限体系、公开异步任务 API、整体模块重构和未经测量的性能承诺。不在本次规格工作中实施代码、创建 worktree 或运行测试。
