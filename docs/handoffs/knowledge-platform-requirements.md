# 本机知识服务需求草案

## 1. 文档目的

本文记录知识服务下一阶段的产品目标和已讨论需求，作为后续方案设计与开发任务的输入。本文描述目标行为，不规定具体类、数据库表或 HTTP 路由。

## 2. 背景与当前基础

当前系统是单机知识服务，启动时指定一个 workspace，已有 HTTP 与 MCP 接入、文档索引与检索、ripgrep 代码搜索、ctags 符号搜索、Git 证据和 LLM 文本生成能力。现有 LLM 主要用于文档/文本块摘要、AI metadata，以及显式 ask 操作的回答生成。

现有实现经过多轮演进，模块和适配层较多。下一阶段应尽量复用已有能力，避免复制整套服务、检索或索引架构。

## 3. 产品目标

构建一个本机运行、可被多个 Agent 调用的知识服务，管理两类知识空间：

1. **公共知识库**：以共享文档和资料为主。
2. **虚拟项目库**：保存虚拟项目信息，并为其关联的代码、需求文档、设计文档及其他资料维护项目级索引。

Agent Memory 不建立第三套存储。它作为虚拟项目库中的文件内容，由同一套文件操作和索引机制管理。

## 4. 核心概念

### 4.1 Workspace

- 服务启动时指定一个 workspace，作为公共知识库及服务自身数据的根边界。
- workspace 中的公共资料和虚拟项目 metadata 属于公共知识服务数据。
- 不将每个 Git 仓库建模为需要用户注册的 workspace 或项目。

### 4.2 虚拟项目

- 虚拟项目是一个可命名、可通过接口管理的逻辑资源集合。
- 每个虚拟项目可以关联多个文件和目录，资源可来自本机任意目录。
- 资源类型不限于源代码；可包含项目需求、设计资料和其他可读取文件。
- 项目 metadata 是公共知识库的一部分。
- 虚拟项目关联的文件内容索引保存在独立的项目索引目录中。
- Git 仓库身份可根据目录中的 Git 特征自动识别，用作来源信息；不要求用户单独注册仓库。

### 4.3 Agent Memory

- Memory 是虚拟项目中文件的一种使用方式，不引入单独的存储模型或生命周期管理系统。
- Agent 可通过明确的文件操作管理 Memory 内容，包括创建、追加、替换、编辑和删除。
- Agent 可使用与其他虚拟项目文件相同的接口和索引机制处理 Memory。

## 5. 功能需求

### 5.1 虚拟项目管理

- 系统必须提供接口创建、查看、修改和删除虚拟项目。
- 系统必须支持向虚拟项目追加、移除文件或目录引用。
- 一个虚拟项目可以包含多个文件和目录；同一资源可按后续实现策略被多个虚拟项目引用。
- 虚拟项目 metadata 至少应能表达稳定标识、名称、描述、资源引用和索引状态。具体字段待设计阶段确定。

### 5.2 本机路径访问策略

- 虚拟项目资源可以位于 workspace 之外的本机目录。
- 管理员可以通过配置规则允许或禁止路径访问。
- 规则冲突时，禁止规则优先于允许规则。
- 路径策略必须同时约束资源加入、目录扫描、同步、读取和文件修改操作。
- 路径检查应基于规范化后的实际路径；符号链接解析不得绕过禁止规则。
- 被禁止或无法访问的资源不得被索引或修改，操作结果应说明资源不可用，但不应泄露未授权路径细节。

### 5.3 索引和同步

- 公共知识库与虚拟项目索引可以采用不同的解析和索引策略。
- 公共知识库优先支持文档检索。
- 虚拟项目索引优先支持代码及项目相关文档检索，并可复用 ripgrep、ctags 和现有文档索引能力。
- 系统不要求实时文件系统监听。
- 内容变化通过显式接口调用或定时服务触发同步和索引更新。
- 两类触发方式应复用一致的同步处理规则。
- 同步应能报告成功、失败及不支持内容类型等状态；具体恢复和增量策略在设计阶段确定。
- 文件引用可指向任意类型，但无法解析或不支持文本提取的文件应被明确标记为不可检索，不得伪报为已成功索引。

### 5.4 搜索与结果融合

- 搜索接口应支持指定虚拟项目。
- 指定虚拟项目搜索时，系统必须检索公共知识库及该项目索引，并合并结果。
- 排序必须对指定虚拟项目中的结果给予额外权重。
- 额外权重使用确定性检索/排序规则实现；搜索排序不调用 LLM。
- 不指定虚拟项目时，只搜索公共知识库。
- 结果必须保留来源信息，至少能够区分公共知识库或虚拟项目，并提供可核查的文件路径、文档或符号定位信息（若来源支持）。
- 搜索结果应标示来源不可用、索引不完整等影响结果完整性的诊断信息。

### 5.5 Agent 文件操作

- 服务必须提供受路径访问策略约束的文件操作接口，支持创建、追加、替换、编辑和删除文件。
- Agent 可通过现有 Agent 接入方式调用这些操作来维护虚拟项目内容及 Memory。
- 每次操作应返回明确结果；失败不得静默吞掉。
- 文件修改后可由显式同步调用或后续定时任务更新索引。
- 是否在写操作成功后自动触发该文件的增量索引，属于设计阶段需确认的行为。

### 5.6 Agent 接入

- 服务保持单机部署形态，并可为多个本机 Agent 提供调用入口。
- 通过 HTTP API 管理虚拟项目、资源引用、同步和文件操作；通过本机 stdio MCP 提供只读搜索，并支持可选虚拟项目范围。
- 不建设 Web UI。
- 服务对多个调用方共享同一公共知识库、虚拟项目 metadata 和索引状态。
- 本阶段不要求跨机器共享、云端部署或远程 Agent 访问。

## 6. LLM 使用边界

- LLM 可继续用于文档摘要、AI metadata 和用户显式请求的 ask/总结回答。
- 普通搜索、索引同步、虚拟项目结果权重和结果合并不得依赖 LLM。
- 本阶段不引入 Codex SDK，也不要求 Agent 自主运行多步代码操作。
- Agent 文件维护通过明确的文件操作接口完成；未来如需自然语言驱动的多步文件整理，再单独评估 Agent SDK。

## 7. 非目标

- 不支持 LSP。
- 不实现实时文件变化监听。
- 不实现跨机器知识同步或远程共享服务。
- 不要求用户手动注册 Git 仓库。
- 不把源文件复制到知识库目录作为索引前提。
- 不为 Agent Memory 建设独立的第三套知识存储。
- 不建设 Web UI。

## 8. 验收标准

1. 操作者可创建一个虚拟项目，并关联来自多个本机目录的文件和目录。
2. 路径 allow/forbid 配置生效，冲突时 forbid 优先；经符号链接或路径形式变化也不能绕过禁止规则。
3. 显式调用和定时任务都能更新虚拟项目索引，并报告处理结果。
4. 指定虚拟项目搜索时，返回公共库与该项目的相关结果，项目结果按确定性规则获得额外排序权重。
5. 未指定虚拟项目时，搜索只返回公共知识库范围内的结果。
6. 搜索结果可以追溯来源库、虚拟项目及原始路径；代码结果在可用时提供符号或行号证据。
7. Agent 可通过接口创建、追加、替换、编辑和删除虚拟项目中的文件；操作受相同路径策略保护。
8. Agent Memory 可按普通虚拟项目文件保存并参与搜索，不需要额外的 Memory 专用存储服务。
9. 普通搜索和结果加权不产生 LLM 调用。
10. 无法读取或无法解析的文件会被清楚报告为未索引或不完整，而不是作为成功索引内容返回。

## 9. 待设计阶段确定

- 虚拟项目 API 和 MCP 工具的具体操作、请求/响应格式及权限边界。
- allow/forbid 配置的文件格式、规则表达方式、默认策略和热更新行为。
- 支持的文件解析类型、二进制文件策略、最大文件大小及目录排除规则。
- 定时同步的调度配置、并发策略、失败重试和索引重建方式。
- 删除虚拟项目或移除资源时，索引目录和 metadata 的清理策略。
- 公共库与项目结果的具体加权公式，以及去重规则。
- 文件操作成功后是否自动触发增量索引。
- 服务的认证要求及多 Agent 调用时的本机访问控制。
- 单机项目数量、索引规模和查询延迟的目标值。
