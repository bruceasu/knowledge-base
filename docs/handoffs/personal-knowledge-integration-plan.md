# 个人知识库与秘书整合方案

日期：2026-10-29。状态：已记录产品方向与目标契约，待分阶段实施。

本文描述目标行为，不表示功能已经上线。本文不修改当前 API、数据库或稳定规格；实施时须按 OpenSpec 工作流更新相应 design、spec、tasks。跨项目 API 的唯一契约定义在 [秘书接入交接文档](personal-secretary-knowledge-handoff.md)。

## 1. 产品定位与决策

知识库是用户长期掌控的个人资料存储与检索服务。个人秘书是主要查询、问答和整理入口。WebUI 主要用于远程上传文件、直接创建笔记、查看处理状态、阅读和维护资料。

- 原文件、笔记及重要元数据可以完整导出，不依赖程序才能阅读。
- 支持现有目录和多种格式，用户不必先整理完文件夹才能使用。
- 秘书通过 HTTP API 接入，不直接读写知识库 SQLite 或索引。
- **目标架构不再需要 MCP。** 不新增 MCP 接入或功能；现有 MCP 在专门实施步骤中移除入口、注册、专属依赖、配置、文档和测试。不能删除仍被 HTTP 使用的检索、上下文或领域模块。
- MCP 移除是明确的兼容性变更，须在实施交付中列出影响和 HTTP 替代方式。本次文档编写不执行移除。
- 用户使用的资料包含 Markdown、TXT、PDF、Word、网页、图片、扫描件，以及 OneNote 导出的 HTML。首版不开发 OneNote 专有协议连接器。

## 2. 架构与所有权

```text
用户 → 秘书 → KnowledgeClient → 知识库 HTTP API
用户 → WebUI ─────────────────→ 知识库 HTTP API
                                ├─ 原件、Markdown 笔记、附件
                                ├─ SQLite 元数据与持久化操作记录
                                ├─ 导入/解析/OCR 后台任务
                                └─ 可重建搜索索引
秘书 → 原有私库：对话、摘要、偏好、计划、授权和执行记录
```

部署基线已确定为不同主机：知识库常驻独立主机，秘书在另一主机运行。一个知识库服务进程持有 workspace。多个调用方访问同一 HTTP 服务，不各自打开资源图。两个项目保持独立部署和独立数据库，不共享 SQLite、索引目录或网络文件系统。知识库由所在主机的服务管理器启动、重启和备份，秘书只连接服务，不远程控制其进程。

| 内容 | 权威来源 |
| --- | --- |
| 上传原件、HTML 资源包、个人笔记、整理成果 | 知识库 |
| 解析正文、OCR、索引 | 知识库派生数据，可重建 |
| 聊天原文、会话摘要、个人偏好 | 秘书私库 |
| 任务、执行授权、凭证、回执 | 现有秘书/平台机制 |

不默认把聊天和秘书记忆全量复制进知识库。用户明确保存的总结可以成为笔记。知识库中的文字不构成执行授权，也不能覆盖秘书政策。

## 3. 文件与组织

- 原始资料、提取内容、整理笔记分别保存。解析或 AI 处理不得覆盖原件。
- 目录用于存放；资料集合、标签和来源用于组织。界面不要求用户理解 workspace、projection 等内部概念。
- 每份资料具有稳定 documentId、版本 revision、contentHash、标题、格式、时间和来源。
- 来源引用尽量定位到页面、章节或文本行；无法定位时返回文档级引用，不编造页码。
- Markdown 是新建笔记的正文格式。完整导出包含原件、笔记、附件、元数据、引用清单和格式版本。
- 文件备份和索引恢复分开：索引可重建，重要整理成果和来源关系必须可恢复。

## 4. WebUI 与导入

首页主要操作为“上传资料”和“新建笔记”，显示最近资料、处理中和失败记录。保留列表筛选、正文预览、编辑、版本和回收站；智能查询由秘书承担，不再优先扩展 WebUI 聊天。

上传流程：保存原件 → 建立持久化任务 → 提取正文 → 发布索引。分别显示“原件已保存”“处理中”“可查询”“部分可查询”“处理失败”。失败可重试，不重复创建原件。

上传大小基线（2026-10-30）：按用户给出的 100 MB 定义单次上传文件内容上限为 100,000,000 字节，包含边界值。首版每个请求上传一个文件或一个 ZIP 包；批量选择拆成多个请求，不以单请求绕过上限。ZIP 按压缩包上传字节计，不代表解压后预算。服务端流式计量，即使没有 Content-Length 也执行限制，超限返回 HTTP 413 并清理未完成的临时文件。前端提前检查用于反馈，最终以服务端为准。代理请求体限制须容纳受限的 multipart 元数据开销，不能将整个 multipart 请求直接限制为 100,000,000 字节而误拒绝合法边界文件。

100 MB 不作为知识库总存储配额，也不改变秘书 JSON 请求的 256 KiB 上限。ZIP 展开总量、文件数、压缩比，以及 OCR 页数、并发、内存和执行时间需要独立预算。

首批支持 Markdown/TXT、HTML 及 ZIP 资源包、文本 PDF、DOCX。后续增加图片/扫描 PDF OCR，旧 DOC 等依据真实样本增加。未支持格式可保留原件，但不能宣称正文已可搜索。

OneNote HTML 以包含 HTML、图片和附件的 ZIP 接入，保留相对关系和原始副本。检查中文编码、相对链接、缺失资源和目录层级；导入报告列明遗漏。ZIP 解压限制文件数、总展开大小、压缩比和目标路径，拒绝路径穿越与越界链接。HTML 预览清理脚本和主动内容，默认不加载远程资源。

后台任务持久化状态，重启可恢复。文件变化的增量同步复用现有机制，后续再接自动触发，避免一次操作反复解析所有资料。

## 5. 知识库对秘书的 API

完整契约见 [personal-secretary-knowledge-handoff.md](personal-secretary-knowledge-handoff.md)，版本 `1.0`，新增前缀 `/api/v2/secretary`。

这是独立适配层，复用现有业务能力，不改变现有 `/api/v2/knowledge/*` 和 `/api/v2/documents` 响应。新接口包括能力查询、搜索、分段读取、创建笔记和按幂等键查询创建结果。

知识库负责：鉴权与范围校验、文档身份映射、稳定分页、引用链接、持久化幂等记录、检索新鲜度和诊断。返回引用内容，不调用 LLM 代替秘书生成最终回答。

## 6. 远程访问

当前服务没有内建认证，不能直接公开现有管理接口。远程开放前必须完成整个服务边界保护，而不只是保护新增秘书路由。

- 浏览器：HTTPS、用户身份认证、安全会话、CSRF 与同源限制。
- 秘书：独立可撤销 Bearer 凭证，按 read/create scope 访问；凭证不得进入模型上下文和日志。
- 秘书到知识库必须使用 HTTPS，校验证书及主机名，不提供跳过校验的生产选项。仅知识库主机内部的代理到后端链路可使用隔离的 HTTP。不能以来源是 localhost 代替服务凭证。
- 上传只写托管目录；远程用户不能提交任意服务器路径。外部目录登记是受控管理操作。
- 文件预览和附件下载也必须鉴权；禁止利用公开链接绕过内容权限。
- 服务不可用不影响秘书普通聊天；保存结果未知时不得误报成功或生成新的保存请求。

baseUrl 是秘书可达的 HTTPS API origin；publicBaseUrl 是用户浏览器可达的 HTTPS 阅读入口，优先使用同一域名。二者不同也必须指向同一个 serviceId，引用链接不得使用秘书或用户不可达的 localhost、容器名或服务器文件路径。断网时秘书继续普通对话，保存结果按幂等键对账。

### 已确认认证方案

用户已于 2026-10-30 确认采用 Caddy + Authelia：Caddy 负责 HTTPS 和反向代理，Authelia 负责浏览器登录与二次验证；知识库负责秘书 Bearer 凭证及 scope/集合权限。浏览器与服务身份分别处理，不让秘书模拟登录或持有浏览器 cookie。

- 浏览器 WebUI、附件、阅读页及浏览器业务 API 统一经过 forward_auth；写操作仍由应用执行 CSRF/Origin 校验。代理登录不能替代应用级写入保护。
- 仅精确匹配 `/api/v2/secretary` 契约的 API 走服务凭证路径，不跳转登录页；后端必须验证 Bearer token。不能以“包含 Authorization header”为条件跳过浏览器认证，也不能放行整个 `/api/v2`。
- 后端只绑定 loopback，或位于不发布后端端口的私有容器网络；外部只能访问代理。当前服务缺少独立 bind-host 配置，实施时需补齐或使用隔离网络，不能只写一条代理配置就认定不可绕过。
- 代理清除外来身份头，再注入认证结果；应用只信任明确配置的代理来源。Authelia 不可用时浏览器入口拒绝访问，不回退匿名。
- 验收覆盖后端直连、伪造身份头、未登录附件访问、未带 token 的秘书 API 和代理认证故障，均不得获得资料。

官方依据：[Caddy forward_auth](https://caddyserver.com/docs/caddyfile/directives/forward_auth)、[Caddy HTTPS](https://caddyserver.com/docs/quick-starts/https)、[Authelia Proxy Authorization](https://www.authelia.com/reference/guides/proxy-authorization/)。选型已确认，尚未部署或实测。

## 7. 分阶段交付

1. 定义并实现秘书 API、身份边界、搜索和读取；秘书完成只读接入。
2. 优化上传与写笔记入口、后台导入和首批格式；完成远程访问保护后开放远程入口。
3. 完成持久化幂等创建笔记，秘书支持将明确要求保存的成果写回。
4. 完整导出、备份恢复、OCR、自动同步及检索质量优化。
5. HTTP 替代能力可用后，移除 MCP 及过时文档。保留领域和检索复用模块。

各阶段分别形成可交付任务；本方案不是对所有实现、依赖变更或发布操作的自动授权。
